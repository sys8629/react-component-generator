# Commit

변경사항을 분석하여 컨벤션에 맞게 커밋하는 스킬. 사용자 승인 없이는 절대 커밋하지 않는다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경·신규(untracked) 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 읽는다.
- 신규 파일은 내용을 직접 읽어 목적을 파악한다.
- 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 종료한다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 파일 단위뿐 아니라 필요하면 변경 덩어리(hunk) 단위로도 나눈다.
- `.env`, 키·토큰, `node_modules`, 빌드 산출물(`dist`) 등은 커밋 대상에서 제외하고, 발견하면 사용자에게 알린다.

### 3. 커밋 메시지 작성
형식: `type: 요약` (한국어, 명령형이 아닌 간결한 서술)

| type | 용도 |
|------|------|
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 |

- 요약은 50자 안팎, 마침표 없이 무엇을 왜 바꿨는지 드러낸다.
- 설명이 필요하면 빈 줄 뒤 본문에 이유와 맥락을 적는다.
- 해당 type이 애매하면 가장 가까운 것을 고른다. 이 4개 외의 type은 쓰지 않는다.
- 메시지 끝에 다음 줄을 붙인다:
  `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`

예시:
```
feat: 결과 창에 코드 줄 수 표시 추가
fix: 프롬프트 입력창 라벨이 연결되지 않던 문제 수정
refactor: 설정 패널 마크업을 공통 창 컴포넌트 구조로 정리
chore: 폰트 CDN 링크와 theme-color 메타 추가
```

### 4. 사용자 승인 후 커밋
- 분류 결과를 아래처럼 보여주고 승인을 받는다. 승인 방법은 AskUserQuestion을 쓴다.
  - 커밋 번호별 메시지
  - 각 커밋에 포함될 파일 목록
  - 제외한 파일과 그 이유
- 사용자가 수정을 요청하면 반영해 다시 보여준다.
- 승인된 뒤에만 커밋 단위마다 `git add <파일>` 후 `git commit`을 실행한다. `git add -A`/`git add .`은 쓰지 않는다.
- 커밋 후 `git log --oneline`으로 결과를 보여준다.

## 금지 사항
- 승인 전 커밋, 그리고 `push`는 사용자가 따로 요청하지 않는 한 하지 않는다.
- `--no-verify`, `--amend`, `reset --hard` 등 이력을 바꾸거나 훅을 건너뛰는 옵션은 명시적 요청 없이 쓰지 않는다.
- 훅이 실패하면 원인을 고쳐 새 커밋으로 만든다.
