# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하거나 단계를 건너뛰지 마라.**

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트별 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.

## 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 에러 매핑)
- **유틸리티 / 순수 함수**
- **버그 수정** (재현 테스트를 먼저 작성해 실패를 확인한 뒤 고친다)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

판단이 애매하면 **적용 대상으로 취급한다.**

## RED-GREEN-REFACTOR

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 설정 오류로 인한 실패는 RED가 아니다. 고친 뒤 다시 실행한다.

### 2. GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지**다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다.
- 삭제는 협상 대상이 아니다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 자주 조용히 깨진다. 테스트도 단순하니 작성 비용이 거의 없다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰 작성되어 결함을 잡지 못하고, 대개 작성되지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. TDD가 더 빠른 경로다. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 테스트 주도로 다시 쓰면 빠르다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 테스트 비용도 작다. |
